# 13 — Translations

- gettext domain: **`big-storage-rescue`** (scripts: `TEXTDOMAIN` in `lib.sh`;
  Python: `gui/common.py`). Catalog: `locale/big-storage-rescue.pot`.
- Languages: `locale/LINGUAS` (pt_BR, as in Big-Mount).
- Sources: `$"…"` strings of the scripts (`bash --dump-po-strings`), `_()` of
  the application (xgettext), the `.desktop` templates and the polkit template
  (ITS rules in `locale/its`). `locale/update-pot.sh` regenerates the template
  and merges it; `locale/compile.sh` builds the `.mo`, the `.desktop` files and
  the policy, which are committed.

## What happened to the translations of Big-Mount

`pt_BR.po` had 1231 translated messages. The renaming script was applied to
`msgid` and `msgstr` alike, so every message kept its translation; two
Portuguese texts about Big-Mount mounting at boot were set back to "Big-Mount"
by hand. After merging with the new template:

| | Messages |
| --- | --- |
| kept, with their translation | 1090 |
| gone or rewritten (automount, Secure Erase, the old `--doctor`, texts that changed) | 141 |
| new or rewritten, translated by hand | 45 (msgmerge guessed 21 of them as fuzzy; every guess was rewritten) |
| total now | 1135, all translated, no fuzzy, no obsolete |

The texts of the boot service stay in Big-Mount's own catalog.

`tests/i18n-tests.sh` checks that the template is up to date, every message is
translated and reviewed, placeholders match, generated files match their
templates, and that the language is chosen at run time (`LANG`, `LANGUAGE`
fallback, incomplete catalog falls back to English).

## Adding a language

```bash
msginit -i locale/big-storage-rescue.pot -l es -o locale/es.po --no-translator
echo es >> locale/LINGUAS
# translate, then
bash locale/compile.sh && bash tests/i18n-tests.sh
```

## No machine translation in CI

The BigLinux translate-and-build workflow (big-auto-translator) was tried and
removed: it machine-translates in CI with an OpenAI key that answered "429 Too
Many Requests", which stopped the job before the build was requested. It also
finds shell scripts by their mime type, so the modules without a shebang were
never extracted, and the `.mo` files it writes would replace the reviewed ones
of `locale/`. `.github/workflows/build-package.yml` only asks for the build.

## Spanish, German, French, Italian, Russian, Chinese, Japanese, Polish, Turkish

Added on 2026-11-03 with the gettext-translation skill, one language at a time:
1. `msginit` from the template, with the `Plural-Forms` of the installed GTK 4
   and libadwaita catalogs (they agree; Turkish has one form there, as in GTK).
2. A glossary from installed catalogs of the same domain (udisks2, kio6,
   the Plasma device notifier, gparted, gtk40, gvfs, Big-Mount's own),
   kept in `locale/glossary/<lang>.tsv` for the next languages and rounds.
3. A translator worked from the msgid, with the reviewed pt_BR text as a hint
   of meaning only, checked by the skill's harness.
4. An independent reviewer read every line against the msgid and the
   rubric, and corrected what was needed:

The reviews also caught errors no mechanical check sees: arguments of a bash
`printf` in the wrong place (zh_CN, ru), "keep aside" (backup) mixed with "set
aside" (stalled files), a quoted button that did not match the button's own
text, and option names (`TARGET`, `FILE`) translated where the help prints them
untranslated. Bash `printf` cannot reorder its arguments, so in the `*.sh`
messages every translation keeps the placeholders in the order of the msgid;
`%%` may move ("%87" in Turkish), and the i18n test allows only that.

msgfmt writes `zh-Hans-CN` in the polkit policy, and polkit looks up
`zh_CN`: `locale/compile.sh` turns both forms of tag into POSIX names, and the
i18n test checks that every language of `locale/LINGUAS` reaches the policy.
